Canton Names

Safe recipient resolution for Canton apps

A drop-in recipient field and typed resolver that lets any Canton app accept readable names instead of party IDs — and warns or blocks before a transfer goes to the wrong party.

The Problem

On Canton, sending value still depends on long, opaque party IDs:

alice::1220a3f9b8c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1c7e2

One wrong character → transfer fails or reaches the wrong party. No way to verify before sending.

Every Canton app that moves value faces this problem.

The Solution

Canton Names is a safe recipient resolution component

Drop-in CnsRecipientInput

One React component with built-in resolution, validation, and confirmation flows.

Typed resolve() contract

Discriminated union on status (ok, missing, expired, unverified, changed) with stable reason codes.

Transfer safety

Blocks missing/expired names. Requires confirmation for unverified/changed. Never sends to the wrong party.

What's Built

Resolver contract

  • Zod schemas for all response types
  • Discriminated union on status
  • Stable SCREAMING_SNAKE reason codes
  • Demo and live resolvers share interface

CnsRecipientInput component

  • Debounced resolution
  • Confirmation checkbox for unverified/changed
  • Blocks missing/expired automatically

How Canton Names Makes Money

Revenue model (planned)

1. Verified names for institutions

Organizations pay for identity-verified names (e.g. bank.cns). Fits Canton's regulated user base.

2. Paid resolver for app teams

Free component; paid tiers add lookup limits, uptime SLAs, and support.

3. Name registration fees

Annual renewal. Premium pricing for short names.

4. Canton network app rewards

Registrations and lookups generate on-chain activity that may earn app rewards.

5. Ecosystem grants

Canton Foundation / AppsFactory funding to bridge to paid tiers.

Revenue model is a plan; nothing is live yet.
